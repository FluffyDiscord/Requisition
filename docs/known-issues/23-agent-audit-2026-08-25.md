# Second audit, 2026-08-25 — nine defects across resolver, networking and hot paths

**Status:** ALL FIXED 2026-08-25 — READY FOR TESTING / HUMAN REVIEW

Three agents audited the resolver, item storage/networking, and per-frame performance
independently. Every finding below was reproduced against `master` by the coordinator before being
accepted — the agent reports were treated as leads, not results.

**Process note worth keeping:** the agent worktrees were created at the upstream commit, which
predated all 22 fixes from the first audit. Two agents caught this themselves and re-based; every
number and trace below comes from a re-run on the correct base. An audit is only as good as the
tree it ran against, and that is worth checking first, not last.

---

## Resolver — the three-way agreement broke again in new places

The invariant from [the first audit](README.md): the recipe grid
(`RecheckRecipeCraftable`), the ingredient squares (`ComputeIngredientPreview` -> `Satisfiable`)
and the craft button (`ResolveRecursive` / `ResolveForceCraft`) must give the same answer.

### 23a. The preview filled a slot from the stock of the item being crafted — HIGH

`CoreResolver.cs` — `ComputeIngredientPreview`'s direct draw

Force-craft semantics say existing stock of the OUTPUT is not a material.
`RecheckRecipeCraftable` removes it, and `ResolveForceCraft` removes it
(`RecipeResolver.cs:524`). The preview's direct draw did neither, so it drew from the very item
being crafted.

Two reachable shapes: the output named as its own ingredient, and — far more common — the output
being a member of an accepted recipe group. `Any Wood`, `Any Iron Bar` and `Any Copper Bar` all
contain items that are themselves recipe outputs.

```
PASS  FD-01 the button refuses: force-craft will not spend the output
PASS  FD-02 the list flag agrees with the button
FAIL  FD-03 the slot is not filled from the item being crafted  [expected 0, got 3]   <-- before
FAIL  FD-04 the preview agrees with the button                                        <-- before
```

A green `3/3` on a dead button: verbatim the complaint that started the first audit, surviving in
a shape its fix did not cover. The agent's 800-world differential fuzz found 110 preview-vs-button
disagreements and every one traced here.

**Fixed:** `ComputeIngredientPreview` removes the output from its pool up front, the same rule the
other two apply.

### 23b. A recipe-group slot one level down committed to a single member — HIGH

`CoreResolver.cs` — `CanProduce`

[Issue 10](10-resolveingredienttype-partial-stock-lockin.md) taught `ResolveIngredientSlot` and
`CanFillSlot` to fill a group slot from a MIX of members. `CanProduce` — the body of all recursive
feasibility — still called `ResolveIngredientType` and committed to one concrete type. The mixing
rule therefore held only at the top level and was lost through every recursion step.

With 3 gold and 7 platinum against a slot needing 10 of either, the plan mixes and succeeds while
the flag and preview both say no: **a craftable recipe hidden from the grid and painted red.**

This makes the README's old "Known remaining divergence" note wrong on both counts —
`ResolveIngredientType` was not confined to shared-confirm ordering, and the plan and preview did
not agree.

**Fixed:** `CanProduce` calls `CanFillSlot`, collapsing the two encodings into one helper. Depth
accounting is preserved: `CanFillSlot(..., depth + 1)` recurses at exactly the level
`CanProduce(resolvedType, ..., depth + 1)` used to.

### 23c. The shared ingredient cache was keyed without the cycle-guard seed — HIGH

`CoreResolver.cs` — `RecheckRecipeCraftable`

`IsIngredientFeasible` seeds the cycle guard with `recipe.OutputType`
([issue 08](08-prefilter-missing-output-cycle-seed.md)'s fix), so a memoised verdict is only valid
for that output. The key recorded it as `ctx`, which was `0` unless the output happened to be in
stock. One `ingCache` is shared across a whole sweep, so verdicts leaked between recipes and
**whichever recipe was evaluated first decided for both** — in either direction: a craftable recipe
hidden, or an uncraftable one offered on a dead button.

Issue 08's file states the key "does not need widening for this fix". It did.

**Fixed:** `int ctx = recipe.OutputType;` unconditionally. Measured cost on the real 14 178-recipe
dump: none — full revalidation is 2 ms before and after, with the same 379 craftable.

### 23d. An aborted craft on a full network destroyed the player's own materials — HIGH

`CraftingTransaction.cs` — `PlanExecutor.Abort`

Introduced by the fix for [issue 22](22-aborted-plan-keeps-its-intermediates.md), the day before.
`Abort` refunded everything the run took — including conjured intermediates a later step had
consumed — and only then discarded them. The transient peak was `original + conjured`, so on a
network with no spare room the refund overflowed by exactly the conjured amount and real materials
dropped as leftover.

```
PASS  AF-02 the wood came back
FAIL  AF-03 the iron came back, not dropped as leftover  [expected 2, got 1]   <-- before
```

Issue 22's claim that "pre-existing stock of the same type is unaffected" was false. The correct
end state is the start state, which fits by definition; the loss was pure sequencing.

**Fixed:** the ledger withholds conjured units *during* the refund instead of re-extracting
afterwards. `RefundLedger` now records each handle's item type, takes `MarkConjured`, and splits
partial handles via a new `ICraftingStorage.SplitOff`. That split also replaced
`IStepProducer.SplitOffExcess`, so there is one split operation rather than two.

## Networking — a client's word was taken for things only the server can know

Calibration: in Terraria multiplayer a client is already authoritative over its own inventory, so
"a modified client gives itself items" is not an escalation. What matters is effect on **shared**
state — the disk network, Drive Bays, other players. Everything below is ranked on that basis, and
all of it except 23f requires a modified client.

### 23e. A withdrawal was routed by a client-supplied index, and `-1` means broadcast — CRITICAL

`NetworkHandler.cs` — `HandleWithdrawItem`, `HandleWithdrawItemByModData`,
`HandleWithdrawItemByFullItemTag`

`playerIndex` came off the wire and became the send target: `resultPacket.Send(playerIndex, -1)`.
The file proves its own broadcast semantics — `packet.Send(-1, -1)` carries the comment "Relay to
ALL clients including the original sender". `HandleWithdrawItemResult` then takes the item with no
check that this client requested anything.

So `playerIndex = -1` pulled a stack from shared storage **once** and handed a copy to **every**
connected client. The authoritative `whoAmI` was already a parameter, and the sender always wrote
`Main.myPlayer`, making the field redundant.

**Fixed:** the field is gone from all three packets and the result is sent to `whoAmI`.
`CraftRequest` carried the same redundant field (read, then correctly ignored in favour of
`whoAmI`); removed too, for consistency.

### 23f. A stray tracking teardown silently desynced every client — MEDIUM, no attacker required

`NetworkHandler.cs` — `HandleWithdrawItemByModData`

```csharp
var modified = StorageWorldSystem.Instance.EndModificationTracking();   // assigned, never read
```

It nulled `_modifiedTracker` and `_preModificationSnapshot`, so the later
`EndModificationTrackingWithDeltas` returned empty, the delta loop was skipped, and
`IncrementDiskSeqNum` was never reached. Success with zero deltas falls through to "confirm only".

The item left server storage and **no client was told** — and because the sequence number never
advanced, the client-side gap detection could not notice either. The withdrawn item stayed visible
in every client's Terminal until a manual resync.

Proof it was an editing slip: the sibling `HandleWithdrawItemByFullItemTag` is identical in shape
and has no such call.

**Fixed:** line deleted. This is the one that fires in ordinary play, on every withdrawal of an
item carrying mod data.

### 23g. Four handlers trusted the packet for things it cannot establish — HIGH

| Handler | Was | Now |
|---|---|---|
| `HandleSyncDiskRemove` | unbounded `slot` into a fixed 40-slot array | bounds-checked |
| `HandleSyncDiskInsert` | same | bounds-checked |
| `HandleRestoreDiskRequest` | no sender at all; remapped any GUID to any GUID | sender must hold the replacement disk; the recovered GUID must be lost or their own |
| `HandleDefragRequest` | no sender at all; any disk list, any order | every disk must be in the sender's reachable network |
| `HandleArchiveDiskRequest` | `Main.player[packetIndex]`; archived the packet's GUID | uses `whoAmI`; the GUID must match the disk in that slot |
| `HandleQuickStackToStorage` | inserted the packet's item payload | inserts the server's copy of that inventory slot |

`Defragment` moves stacks from later disks into earlier ones, so an attacker-ordered list drained
one player's disk into another's. `RemapDiskData` moved a disk's whole contents to a caller-chosen
GUID. Disk GUIDs reach every client (`StorageDiskBase.NetSend` transmits all 16 bytes), so naming
one proves nothing.

**Fixed** via a shared `GetReachableDiskIds(whoAmI)` — the union of the networks of Terminals
within 15 tiles of the sender, matching the range quick-stack and position-deposit already enforce.
`HandleDepositItemAtPosition` was already the correct model and is unchanged.

**Deliberately permissive:** recovery still allows remapping a GUID whose disk the sender holds,
because the recovery list shows every non-empty disk rather than only lost ones, and refusing that
would break a reachable UI action. Only *other people's* live disks are refused.

### Reported but not fixed

A forged disk item can carry attacker-chosen `DiskId`, `Tier` and `ArchivedItems` through
`StorageDiskBase.NetSend` into `RegisterDiskWithItems`, which overwrites unconditionally. Also:
unbounded `new List(count)` from wire-supplied counts, and `SnapshotItems` / `ApplyDeltaToDisk`
dropping `FullItemTag`. These were reported but **not independently verified**, so they are not
fixed and should be treated as open leads rather than established defects.

## Performance — measured, not guessed

### 23h. Search re-parsed per item with culture-sensitive comparison — 40% of a frame per keystroke

`ItemSearchHelper.cs` — `Parse`

`search.StartsWith("#")` takes the `string` overload, which defaults to **current-culture**
comparison through ICU. `Matches` called `Parse` once per item, and five sweep sites call `Matches`
per item.

```
14178 recipes x 2 StartsWith (one keystroke):
  StartsWith("#")           =  6,725 ms   <-- shipped
  StartsWith("#", Ordinal)  =  0,003 ms   (2242x faster)
  StartsWith('#')           =  0,003 ms   (2242x faster)
```

6.7 ms against a 16.67 ms frame budget, on every keystroke, before any actual matching.

**Fixed:** `Parse` uses the `char` overload (ordinal by nature), and a pre-parsed
`Matches(itemType, mode, query)` overload lets sweeps parse once. All five call sites hoisted.
The per-item `Substring(1)` allocation goes with it.

### 23i. `Defragment` allocated per donor stack; the panel's scratch dictionary hit the LOH

`StorageWorldSystem.cs` — `Defragment`; `UICraftingPanel.cs` — `SyncFilteredRecipesIncremental`

`BuildMergeTargets` allocated a list for every donor stack inside a triple loop — at the supported
maximum (40 disks x 2048 stacks) that measured **869 MB of churn and a 376 ms freeze**. `GetMaxStack`
also built a fresh `Item` per stack.

Separately, `new Dictionary<Recipe, bool>(_allRecipes.Count)` measured **408 768 B** — well over the
85 000 B Large Object Heap threshold — allocated several times a second during the deferred
recursive pass, buying a gen2 collection every ten calls. Gen2 pauses are the ones players feel.

**Fixed:** the defrag buffers and the plan object are hoisted and reused (`DonorMovePlan.Reset`,
a `PlanDonorMove` overload taking a caller-owned plan), `maxStack` is cached per item type, and the
panel keeps one scratch dictionary and `Clear()`s it — measured at 0 B on reuse.

**Time half fixed 2026-08-26.** The allocation fix cut churn ~66x but time only ~1.08x, because the
rescan itself was the cost. `Common/MergeCandidateIndex.cs` now buckets the target disk's stacks by
`(ItemType, PrefixId)`, rebuilt once per target and appended to as the sweep grows the disk, so a
donor is offered only the stacks that could take it instead of all 2048.

The key is deliberately **weaker** than the merge rule, and that is the whole safety argument:
`StoredItemStack.StacksWith` refuses a different type or prefix before it tests anything else, so
sharing the key is a *necessary* condition of merging and never a sufficient one. `Accepts` is
still assigned only from `DiskData.CanMergeStacks`, so the index can only ever withhold a pair the
rule would have refused — it can never claim one merges. A missed merge leaves a stack where it is;
that is the only direction this can fail in, which is what keeps it clear of [04](04-defragment-destroys-per-instance-data.md)
and [24](24-globaldata-treated-as-item-identity.md). `MX-01` pins the candidate set against the
linear rescan it replaces, and `MX-08`/`MX-09` pin the two source facts that make the key safe.

Measured by `Tests/HotPathBenchmarks.cs` at the supported maximum, 40 disks x 2048 stacks. Figures
are one machine's run, quoted to two significant figures because a single `Stopwatch` reading does
not support more; the committed benchmark prints live numbers.

| | before | after |
|---|---|---|
| fragmented disks | **~340 ms**, 3.6 MB | **~21 ms**, 3.5 MB (~x16) |
| bulk storage (8 types, 90% full stacks) | **~690 ms** | **~24 ms** (~x29) |

**These ratios are an upper bound, not a floor.** The replica cannot call `ItemLoader.CanStack` or
`ItemIO.Load`, so where the real merge rule reaches `GameAllowsStacking` — a plain donor weighed
against a candidate that stands for itself — the replica exits early instead. The index does not
change how many comparisons reach that point; it only removes the ones that exit on the type check.
So every cost the replica omits shrinks the real ratio. It stays small because the dominant kept
comparisons are plain-against-plain, which never reach `GameAllowsStacking` — but it is not zero,
and nobody has bounded it.

Two things the original note got wrong, both found by review:

- The benchmark's replica skipped the `TagCompound` comparison, and the missing cost lands entirely
  on the comparisons the index **keeps** — it prunes the pairs that exit on the type check, which
  are the cheap ones. So the replica overstated the speedup rather than understating it. Running the
  full `ModStateMatches` moved the figure from x17.1 to x10.3; making `ModStateMatches` itself
  cheaper then brought it back to ~x16. The same argument still applies to `ItemLoader.CanStack`,
  which the replica cannot call — see the bound above.
- A bulk-storage disk defeats a `(type, prefix)` index on its own: `DiskData.InsertItem` bounds the
  number of *partial* stacks per identity, not the total, so half a million Stone is hundreds of
  full stacks in one bucket. `BuildMergeTargets` therefore passes over any candidate already at
  `maxStack` — which `PlanDonorMove` would have skipped anyway — before paying for the identity
  comparison. Without that, the 686 ms row barely moves.

One assumption the index makes load-bearing, recorded rather than fixed: the sweep now holds slot
positions for a whole target disk instead of rebuilding them per donor stack, so "nothing outside
`Defragment` touches these lists mid-sweep" went from a microsecond window to a whole `ti`
iteration. `DiskData.ExtractItem` and `ExtractItemWithFullItemTag` both call `Items.Remove`, which
would invalidate recorded slots. Nothing was found dispatching those off the main thread, so this
is not a known race — but `BuildMergeTargets` now bounds-checks each slot so that if it ever
becomes one, the cost is a missed merge rather than a count credited to the wrong stack.

Two defects surfaced on the way and were fixed in the same pass:

- `ModStateMatches` built two throwaway `TagCompound`s per call purely to hand the pair to
  `TagCompoundEquals`, which for a single key reduces to comparing the two values: ~210 ns / 432 B
  per call became ~120 ns / 0 B. A `ReferenceEquals` fast path settles a self-comparison in 2 ns;
  that fires for every pair in an unmodded world and for none in a heavily modded one, so it is
  free insurance rather than the main saving.
- `HandleDefragRequest` took the disk list off the wire and checked each id only for *reachability*
  — never the count, never for repeats. Three separate holes, all on the path this change touches:
  `ReadGuidList` pre-sizes a list from an attacker-chosen `int` (remote out-of-memory); one
  reachable id repeated fills the list legally and `Defragment`'s sweep is quadratic in disk count
  (server stall); and a repeated disk made itself its own donor, which with an index is far worse
  than before, because `donor.Items.RemoveAt` shifts every slot the index recorded and counts land
  on a stack of an unrelated item type. The count is now bounded by what the sender can reach,
  repeats are rejected at ingest, and `Defragment` keeps `ReferenceEquals(target, donor)` as
  defence in depth for the single-player caller. Pinned by `MX-11`.

### Measured and already fast — do not re-optimise

Full craftability revalidation over the real dump (1–2 ms, 0 gen0 GCs); `DiskData.ExtractItem` via
`StackSelection` (96 B per extract); `PlanExecutor.Run` (~1 KB per craft, and a craft is one click);
the favorites panel (0 B over 10 000 frames, held by `FC-06`); the output-slot and disk-panel
counts, both version-gated. Three further suspicions were measured and dropped as debounced or
already memoised.

## Guard against recurrence

`FD-*`, `NG-*`, `IO-*`, `AF-*` — 26 assertions covering the four resolver and transaction fixes.
The networking and search fixes have no unit-test surface for the reasons
[21](21-untested-fixes.md) sets out; the networking set still needs a real two-client session.

The lesson from this round, on top of [21](21-untested-fixes.md)'s: **a fix that establishes a rule
must be applied at every site that encodes it.** 23a, 23b and 23c are each the same shape — a rule
introduced in one place while a second or third encoding of it kept the old behaviour. 23d is the
same again, one day later.
